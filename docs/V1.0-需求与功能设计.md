# 医疗健康智能助手：需求、前端设计与开发功能划分

**版本：** V1.0\
**日期：** 2026-10-14\
**定位：** RAG + 可控 Agent + 医疗知识证据追溯

## 一、项目定位与目标

本项目定位为以 RAG 为知识基础、以 Agent
为任务执行与编排能力的综合型医疗健康智能助手。系统先从医疗知识库检索相关证据，再根据问题决定是否调用工具、补充检索或核验，最终生成有来源依据、带适当安全提示的回答。

第一阶段采用可控的单 Agent + 工具调用 + RAG，不把复杂 Multi-Agent
作为前置条件。

### 设计原则

1.  医疗回答优先基于可追溯证据。
2.  简单问题走简单链路，不要求所有问题都进入 Agent 循环。
3.  工具调用有允许列表、Schema、最大轮数、超时和预算限制。
4.  不替代医生诊断，不生成不适当的个体化治疗指令。
5.  通过测试集和失败案例优化，而非只凭主观判断。
6.  先检查现有代码和真实运行链路，再决定修复、重构或新增。

### 目标用户与阶段

-   **第一阶段：普通用户为主。**
    常见健康知识、疾病科普、检查指标基础解释、一般性就医指引。
-   **第二阶段：医学生。**
    医学概念、疾病机制、专业术语、知识点对比和来源追溯。
-   **第三阶段：医学研究人员。**
    专业文档检索、多来源证据整理比较、研究结论与不确定性追溯。

三类用户共用底层文档处理、检索和模型调用能力，按阶段扩展交互与工作流。

### 第一阶段范围

**纳入：** PDF 上传与入库、RAG 检索、Query
Rewrite、Reranker（基于现有实现验证）、答案生成与引用、Agent
意图判断、受控工具调用、基础多轮对话、安全降级、评估、日志和配置完善。

**暂不纳入：** 自动诊断、处方决策、复杂 Multi-Agent
医疗会诊、大规模外部数据源接入、系统性文献综述。

## 二、需求说明

### 2.1 用户需求

  编号   需求                 期望结果
  ------ -------------------- ------------------------------------
  U1     提出健康问题         获得清晰回答
  U2     查询医学资料         返回相关知识和来源
  U3     核对答案依据         能追溯真实文档与片段
  U4     连续追问             保留必要上下文，并在需要时重新检索
  U5     知识库缺少证据       明确说明限制，不编造结论
  U6     提出潜在高风险问题   给出适当安全提示与就医引导
  U7     维护知识库           上传文档并查看处理结果

### 2.2 业务需求

  编号   需求             说明
  ------ ---------------- ------------------------------------
  B1     医疗知识问答     通过 RAG 生成基于证据的回答
  B2     文档管理         上传、解析、切分、向量化和入库
  B3     检索与排序       召回相关内容，按需重排
  B4     Agent 路由       决定直接走 RAG 或调用工具
  B5     工具调用         按 Schema 调用允许的工具并读取结果
  B6     答案核验与引用   检查来源是否真实、是否支持结论
  B7     安全与降级       处理证据不足、工具失败和高风险问题
  B8     评估与调试       比较检索、回答和 Agent 路由效果

### 2.3 非功能需求

-   稳定性：常见异常有明确处理，不因单次模型或工具错误导致服务崩溃。
-   可维护性：模型、Embedding、向量库路径、API 地址集中配置。
-   可观测性：记录请求
    ID、检索结果、工具调用、耗时和错误类型；不泄露密钥。
-   可复现性：提供环境配置、启动命令和测试方法。
-   安全性：输入校验、工具允许列表、最大执行轮数和超时。
-   可扩展性：RAG、工具、路由和回答生成职责清晰。

## 三、前端设计

### 3.1 页面结构

建议采用主聊天页面 + 知识库管理入口的轻量结构。

**A. 主聊天页面**

-   顶部栏：产品名称、知识库状态、知识库管理入口。
-   左侧栏（可选）：新建对话、历史会话；若暂未实现会话持久化，可先不做复杂历史。
-   中央对话区：用户问题、助手回答、加载状态和错误状态。
-   回答区域：回答正文、风险提示、引用来源和必要的检索依据。
-   底部输入区：多行输入框、发送按钮；只有后端支持真实中断时才展示停止生成。
-   状态提示：检索中、生成中、完成、证据不足、请求失败。

**B. 知识库管理区域**

-   PDF 选择与上传。
-   文件名、上传时间和处理状态。
-   解析、切分、向量化的成功或失败状态。
-   可读的失败原因。
-   已入库文档列表。
-   如果实现删除，必须同步删除该文档对应的向量和元数据。

**C. 引用详情**

-   文档名称。
-   页码或章节（若源文件可提供）。
-   命中的原文片段。
-   引用与回答对应结论的关联。

引用必须来自检索链路的真实元数据，不能由模型凭空生成文档名或页码。

### 3.2 关键交互

  场景             前端行为
  ---------------- ------------------------------------------------
  正常提问         显示处理中状态；后端真实支持流式时逐步展示回答
  回答完成         展示正文、来源引用和必要提示
  无相关证据       显示知识库未检索到足够依据等说明
  上传成功         显示处理成功状态
  上传失败         显示可理解的原因并允许重试
  模型或工具异常   展示错误，不泄露堆栈、密钥或内部配置
  连续追问         保留必要上下文，不同会话之间不得串数据
  生成中断         只有后端确实支持中断时才提供该操作

### 3.3 视觉与体验原则

-   医疗健康风格清晰、克制、可信，不使用夸张的诊断式视觉表达。
-   回答、风险提示、引用来源在视觉上明确区分。
-   不使用"已确诊""保证准确"等绝对化表述。
-   加载、空状态和错误状态都要有反馈。
-   第一阶段优先保证桌面端主流程可用。
-   不显示没有后端能力支撑的按钮或状态。

### 3.4 前端验收标准

1.  提交问题后能正确展示处理中、成功或失败状态。
2.  回答完整，引用可以展开查看。
3.  上传 PDF 后能看到处理结果。
4.  网络错误、后端错误和无证据场景有明确反馈。
5.  API 地址从统一配置读取，不分别硬编码不同主机地址。
6.  流式展示与后端实际能力一致。
7.  不展示伪造引用、虚假处理状态或未实现功能。

## 四、功能模块划分与验收标准

### F1. 文档与知识库管理

**功能：** PDF 上传与校验、解析、清洗、Chunk
切分、元数据生成、Embedding、Chroma
入库、处理状态与错误反馈；后续再做重复文件检测、更新和删除。

**验收：** - 合法 PDF 可以解析、切分并入库。 -
非法、空文件或解析失败不会被误报成功。 - Chunk
保留文档标识和必要来源信息。 - 入库后可检索到对应内容。 -
更新或删除时，向量和元数据保持一致。

### F2. RAG 检索

**功能：** 向量检索、Query
Rewrite、Reranker、来源元数据返回、无结果处理；后续按评估结果考虑
BM25、混合检索和过滤。

**验收：** - 返回结果含可追溯来源元数据。 - Query Rewrite 与 Reranker
可以单独启用、关闭和对比。 - 使用固定测试集记录 Recall@K、MRR 等指标。 -
无可靠结果时不伪造证据。

### F3. 医疗问答生成

**功能：**
组织问题与证据、模型生成、回答格式控制、必要上下文管理、模型异常处理。

**验收：** - 有证据时回答与证据一致。 - 证据不完整时说明不确定性。 -
无证据时不编造引用或结论。 - 模型异常时前后端正确处理。

### F4. Agent 路由与任务编排

**功能：** 判断问题类型与风险、决定直接走 RAG
或调用工具、生成并校验参数、执行工具、读取结果、决定继续或结束、限制轮数与预算。

**验收：** - 预设问题类型有合理执行路径。 -
简单问题不做无意义的多轮调用。 - 参数符合 Schema。 -
工具失败不会被当作成功结果。 - 不发生无限循环。 -
关键路由决策和执行步骤可追踪。

### F5. 医疗工具

  -------------------------------------------------------------------------------
  候选工具                     用途                    边界
  ---------------------------- ----------------------- --------------------------
  `search_medical_knowledge`   检索医疗知识库          返回真实检索证据与来源

  `get_document_detail`        获取文档或片段详情      仅访问允许范围内的资料

  `explain_medical_term`       解释专业术语            不包装为个体诊断

  `check_emergency_guidance`   识别预设紧急风险信号    仅用于安全提示和就医引导
  -------------------------------------------------------------------------------

以上是拟定的逻辑工具，需代码审查后决定复用、封装或新增。

**验收：** 每个工具有明确输入
Schema、输出结构和错误语义；调用过程可追踪；不虚构数据；异常、超时、非法参数和空结果均有处理；工具权限受限。

### F6. 安全与引用

**功能：**
来源引用、证据不足降级、高风险问题提示、事实与推断区分、安全边界检查。

**验收：** - 引用来源真实存在，且支持对应结论。 -
不仅凭有限文字信息给出确定诊断。 -
不随意生成危险的个体化用药或治疗指令。 - 预设紧急风险场景有适当提示。 -
安全关键用例逐条通过，不以平均分掩盖严重错误。

### F7. 对话与前端交互

**功能：**
提问、回答、加载状态、流式响应、引用展开、文件上传、错误提示、多轮上下文。

**验收：** - 主聊天流程完整可用。 - 回答与引用正确展示。 -
不同会话的数据不串用。 - 前端错误状态与后端响应一致。 -
不展示未实现功能。

### F8. 评估与工程化

**功能：** 固定测试集、检索评估、答案和引用评估、Agent
路由与工具评估、统一配置、日志、异常处理、启动文档和自动化测试。

**验收：** - 测试集与评估命令可重复运行。 - 能对比基础 RAG 与 Agent +
RAG。 - 能定位典型失败案例。 - 日志不泄露密钥或不必要的敏感信息。 -
项目能按文档在目标环境启动。

## 五、第一轮验收指标建议

以下为工程起步目标，需用真实测试集校准，不代表行业统一标准，也不能单独证明医疗安全性。

  指标                          第一轮目标 方法
  -------------------- ------------------- ----------------------------
  核心流程基础用例               100% 通过 上传、检索、回答端到端测试
  工具 Schema 合规率                  100% 检查输入参数和输出结构
  无限循环                            0 次 注入异常和重复调用场景
  Recall@5                     目标 ≥ 0.80 对照人工标注的相关证据
  引用真实性                          100% 核验来源是否真实存在
  引用支持性                   目标 ≥ 0.85 人工核查引用是否支持结论
  安全关键用例           100% 通过预设用例 逐条检查高风险场景
  环境复现                  按文档成功启动 独立环境验证

建议先准备 30--50
个典型问题，覆盖普通科普、专业术语、无相关资料、多轮追问、工具异常和高风险问题。这个规模适合作为起步测试集，不足以证明系统具备临床安全性。

## 六、开发任务与优先级

### P0：现有系统盘点与 RAG 稳定化

1.  确认真实运行入口和调用链。
2.  统一 API Key、模型、Embedding、向量库路径和前端 API 地址。
3.  确认 PDF 入库、检索、重排、生成和引用链路。
4.  修复主流程问题并增加基础测试。
5.  确认现有流式接口是否为真实模型流式生成。

**交付物：** 可复现的 RAG 主流程、配置说明、基础端到端测试。

### P1：Agent 最小闭环

1.  定义问题类型与路由策略。
2.  将 RAG 封装为 Agent 工具。
3.  定义工具 Schema 和返回格式。
4.  实现工具调用与结果回传。
5.  增加最大执行轮数、超时和错误处理。
6.  测试简单直答、需要检索和工具失败场景。

**交付物：** 可控的单 Agent + RAG 闭环与工具调用测试。

### P2：安全、引用和评估

1.  建立固定问答测试集。
2.  对比基础检索、Query Rewrite、Reranker。
3.  核验引用真实性与支持性。
4.  增加高风险与无证据场景测试。
5.  记录 Agent 路由与工具调用过程。

**交付物：** 可重复评估脚本、指标结果和失败案例清单。

### P3：前端与产品体验完善

1.  完善回答、引用和风险提示展示。
2.  完善上传、错误状态和重试体验。
3.  根据后端能力实现真实流式响应。
4.  补充必要的会话上下文管理。
5.  完善启动说明和演示流程。

**交付物：** 可演示、可复现的第一阶段产品版本。

### P4：后续增强

根据评估结果决定是否增加医学生模式、研究人员文献检索、文档更新删除、BM25/混合检索、复杂
Agent 工作流、多 Agent、Docker 和更全面的自动化测试。

## 八、第一阶段完成定义

第一阶段完成时应满足：

1.  医疗 PDF 能处理并建立知识库。
2.  用户能提出问题并获得基于证据的回答。
3.  回答能展示真实、可追溯的来源。
4.  Agent 能在受控范围内选择 RAG 或调用工具。
5.  工具异常、无证据和高风险问题有明确处理。
6.  检索、答案、引用和 Agent 行为有基本评估方法。
7.  前后端配置统一，项目可按文档复现。
8.  能解释系统架构、关键设计取舍和已知限制。

**执行原则：先盘点现有代码，再建立需求---代码映射，最后按 P0 → P1 → P2 →
P3 推进。先复用、再修复、必要时重构，避免推倒重写或无限扩展功能。**
