## 5. 四类业务能力的真实覆盖情况

本次用真实检索实测了四类问题（距离为 L2，越小越相关）：

| 业务类别 | 知识库覆盖 | 实测代表性结果 | 能否处理 |
|:---|:---|:---|:---|
| **药品信息**（说明书类） | ✅ 11 份说明书 | 「二甲双胍的适应症是什么？」→ 0.530 命中正确 PDF | 可以 |
| ① 常见健康知识 | ❌ 几乎为零 | 「熬夜对身体有什么影响？」→ 0.895~0.980，返回氨氯地平/二甲双胍说明书 | **不能** |
| ② 疾病科普 | ⚠️ 仅附着于药品适应症 | 「感冒了怎么办？」→ 0.951~0.965，返回来那度胺说明书 | 仅极有限 |
| ③ 检查指标基础解释 | ❌ 无独立内容 | 「血压的正常范围是多少？」→ 0.596 命中氨氯地平说明书（**含量效数据，不含"正常范围"**） | **不能** |
| ④ 一般性就医指引 | ❌ 完全没有 | 「我胸口疼要去哪个科？」→ 0.925~1.102，返回来那度胺不良反应表 | **不能** |

**关键量化发现：** 相关与非相关问题存在可用的区分带——

- 库内有覆盖：距离 **0.53 ~ 0.80**
- 库内基本没有：距离 **0.89 ~ 1.10**

约在 **0.85** 附近可分离。注意 ③ 类（0.60~0.83）会落在"相关"一侧，但文档中**并不包含所问的答案**——说明只靠距离阈值无法解决 ③，需要额外的"证据是否支持结论"判定。

**这是本次最重要的结论：** 在把 RAG 接进 Agent 之前，必须先有「证据是否足够」的判定。否则 Agent 会把 ①②③④ 类问题全部路由进 RAG，拿回无关的说明书片段，然后由 LLM 基于这些片段作答——这正是需求 U5 / F6 要防的编造风险。

**知识库内容扩充（①②③④ 类资料）是一个数据任务，不在本次代码范围内，但它是这四类业务能否成立的前置条件。**

## 7. 下一个开发节点

### 结论：先做 **P0-RAG 稳定化 + 证据充分性判定**，暂不做 Agent 路由

**为什么不是直接做 Agent：** 四类问题里有三类当前知识库根本没有依据。在这个前提下先写路由，路由只能"正确地"把问题送进一个必然返回无关片段的检索器，然后把无关片段当证据生成答案。**路由的前提是检索器能可靠回答"我有没有依据"。** 这个能力现在不存在，且需求文档 P0 也正是要求先做"现有系统盘点与 RAG 稳定化"。

### 本节点要做的事（复用优先，不重写）

1. **统一配置**：新建 `backend/app/config.py`（或复用根 `.env`），集中 API Key、模型名、base_url、Embedding 路径、向量库路径、相关性阈值。把 `chain.py` / `store.py` / `ingest.py` / `clear.py` 里的 6 处硬编码收敛过来。
2. **修复主链路**：解决 `langchain_chroma` 依赖（安装或在 `requirements.txt` 中声明；`store.py` 用 `langchain_community` 版本也能跑，二者选一统一）。把 `CHROMA_DIR` 统一到真实的 `backend/chroma_db`。
3. **新增相关性判定**：在检索结果上按距离阈值（初值取实测分离带 **0.85**）判定证据是否充分，不足时返回明确的「知识库暂无足够依据」信号——**不把无关片段交给 LLM**。阈值必须用测试集校准，不能拍脑袋。
4. **补齐 `requirements.txt`**：把实际 import 但未声明的包补上，保证 `pip install -r` 后能跑。
5. **修 `metric/eval.py` 路径**，使其能在本机跑出 Recall@3 / MRR，并**扩充测试集**到覆盖四类业务 + 无依据类用例（现 28 条全是药品类）。
6. **只做最小前端修复**：`react-markdown` 依赖声明 + 统一 API 地址。其余体验问题留到 P3。

## 8. 能力归属划分（复用现有代码）

### 8.1 由 RAG 提供（复用 `store.py` / `chain.py`，不重写）

| 能力 | 归属 | 理由 |
|:---|:---|:---|
| 向量检索 + 来源元数据 | RAG | `store.py:search()` 已实测可用 |
| Query Rewrite | RAG（可选开关） | `store.py:rewrite_query()` 已存在，待验证 |
| Reranker 精排 | RAG（可选开关） | `store.py:search_with_rerank()` 已存在，模型文件已确认在本地 |
| 基于证据的答案生成 | RAG | `chain.py:get_rag_chain()` 已存在，待修复 |
| **相关性 / 证据充分性判定** | **RAG 层（需新增）** | 属于检索质量，不应由 LLM 凭感觉判断 |

### 8.2 由主 Agent 负责（不封装成工具）

- 判断问题属于四类中的哪一类
- 决定"直接答 / 走 RAG / 调工具 / 拒答并引导就医"
- 组织最终回答、引用展示、风险提示
- 轮数、超时、预算控制

**理由：** 这些是编排决策本身，如果也做成"工具"，模型需要先决定"要不要决定"，会引入无意义的额外轮次，正好违反需求 F4「简单问题不做无意义的多轮调用」。

### 8.3 适合封装为工具（供 Agent 按 Schema 调用）

| 工具 | 实现方式 | 复用情况 |
|:---|:---|:---|
| `search_medical_knowledge` | RAG 检索（含相关性判定）的薄封装 | **复用** `store.py` / `chain.py` |
| `check_emergency_guidance` | **纯规则**关键词匹配（胸痛、呼吸困难、意识障碍等）+ 固定就医引导文案 | 新增，无需 LLM，覆盖第 ④ 类业务与 F6 高风险场景 |
| `explain_indicator_reference` | 检查指标参考区间查询 | **依赖知识库扩充**；库中无资料前不做，或仅返回"暂无资料" |
| `get_document_detail` | 按文档 ID / 页码取原文片段 | **复用** `chain.py:extract_sources` 的元数据 |

### 8.4 适合封装为**普通函数**（不进工具列表）

- BMI 计算（`agent/tools.py:get_bmi` 已有，可搬用）
- 单位换算、阈值区间查表
- 文本清洗

**理由：** 这些是确定性计算，不需要模型"决定何时调用"，也无需占用 token 预算。

### 8.5 四类业务的目标路由（P1 落地方向）

| 问题类别 | 路由 | 落地方式 |
|:---|:---|:---|
| ① 常见健康知识 | RAG → 证据不足则明确告知 | 复用 RAG + 相关性判定 |
| ② 疾病科普 | RAG → 证据不足则明确告知 | 同上 |
| ③ 检查指标基础解释 | RAG → 证据不足则明确告知 | 同上（当前多数会落到"证据不足"，属**正确行为**） |
| ④ 一般性就医指引 | **不走 RAG**，走 `check_emergency_guidance` + 固定引导文案 | 规则工具 |
| 高风险 / 紧急信号（横切） | 强制插入风险提示与就医引导 | 规则工具，优先级最高 |

## 9. 是否需要引入 LangGraph

**结论：本阶段不引入。**

- 现有的两份 langgraph 代码（`agent/workflow.py`、`multi_agent_business/graph.py`）都是无关演示，不能复用。
- P1 的目标是**单 Agent + 受控工具调用**，用 `openai` 原生 tool-calling 循环即可表达（`agent/agent_loop.py:88` 的 `while True` + `tool_calls` 判断就是可用形态），只是需要补上最大轮数、超时、异常处理。
- 引入 langgraph 会同时引入状态定义、检查点、图编译等概念，在职责边界尚未稳定时属于需求文档 §五「不提前引入不必要的复杂架构」所禁止的。

**建议：** P1 先用显式循环实现（代码可读、易调试）。等出现"多分支 + 需要在节点间持久化状态"的真实需求时，再评估迁移。
