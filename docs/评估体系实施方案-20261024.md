## 一、现状审查：已有的与缺失的

### 1.1 已有资产（全部可直接复用）

| 资产 | 位置 | 能力 | 状态 |
|---|---|---|---|
| 检索级覆盖集 | `acceptance/coverage.py` | **8 组 110 题**（P0/P1A/P1B/PA/P1C/P2A/P2B/EXT），带 `expect_docs` 人工标注；逐题记录 hit_rank/top1/距离/摘录；`classify()` 失败分类（RETRIEVAL_OK / RETRIEVAL_MISS / KNOWLEDGE_MISSING / EVIDENCE_INSUFFICIENT） | ✅ 可用，7 条单测锁定分类口径 |
| 72 题链路集 | `acceptance/health72.py` | 12 领域 × 6 题（2026-10-21 冻结），检索级 + `--chat` 链路级，逐题证据落盘 | ✅ 可用 |
| 验收门禁 | `acceptance/cases.py` + `runner.py` | 48 条 pass/fail（急症/拒答/空结果/模糊/多轮/隔离/分类边界/计算）+ FR-01 诊断 8 条；blocked 语义、redact、登录自举 | ✅ 可用，13 条 harness 单测 |
| 引用支持率诊断 | `acceptance/fr01.py` + `support.py` | T-16-lite 字符 8-gram 支持率（**仅诊断**）；官方口径 = 人工核对 ≥0.85（FR01人工核验记录.md，AI 辅助核验 100% 待人工抽查） | ✅ 可用，口径已区分 |

| 实验脚本 | `scripts/calibrate_threshold.py`、`eval_pa03_*.py` | 一次性实验 + JSON 原始数据范式（本方案的报告格式沿用此范式） | ✅ 范式复用 |

### 1.2 明确缺失 / 不可用的

| 缺口 | 现状 |
|---|---|
| **聚合指标计算** | coverage/health72 只逐题落盘 hit_rank，**不算** Recall@K / MRR，无跨组汇总；每轮靠人眼读 JSON |
| **metric/eval.py** | 仓库根的 28 题 Recall/MRR 原型是**死代码**：`sys.path.append("/app/rag")` 路径无效、`from store import ...` 依赖设计文档已判不可用的 store.py（无效路径、非包内导入）。**不可复活，方案中弃用** |
| **答案准确率** | 无任何"答案是否正确"的度量；FR-01 自动指标是 n-gram 重合，口径粗、仅诊断 |
| **幻觉/拒答的量化** | 正确拒答有 T-02b（3 题）守着；**误拒答率**只在 72 题报告里人工数过（B 类 18 题那次），没有每轮自动算；无"无依据断言率"；无证据冲突场景 |
| **错误归因自动化** | A~S 分类体系（覆盖分析报告）是**人工**逐题分的；run JSON 里没有机器可归因的字段输出 |
| **Prompt 版本管理** | 生产 5 份 Prompt（CLASSIFY / RESOLVE / JUDGE / MEDICAL + 安全词表）零版本记录，改完只能靠 T-14b 等电池防回归，无法回答"这轮指标变化是哪次 Prompt 改动引起的" |
| **报告与版本对比** | 每次运行产出孤立 JSON；无 Markdown 报告、无运行元信息（Prompt 哈希/模型配置/索引版本/git SHA）、无与基线的 diff |
| **NDCG** | 无分级相关性标注（只有"相关/不相关"二元），NDCG 退化为与 Recall 同序——**建议不做**，除非先建分级标注（成本不值） |

### 1.3 设计约束（从现状推出的原则）

- 评估代码放 `backend/acceptance/` 内扩展（它已经是事实上的评估 harness），**不新建顶层框架**；
- 指标计算必须是**纯函数**（输入 run JSON → 输出指标），与执行解耦——这样单测可锁公式，历史 JSON 也能重算；
- 三类评估的边界保持现状口径：**确定性单测**（225 个）/ **离线检索评估**（零 LLM）/ **真实 LLM 端到端**（门禁 + 72 题），报告里三者分开展示，不许混算；
- LLM 裁判**不作为指标**：方案中所有自动指标都是确定性的；LLM 只能出现在"模型辅助、单独标注、可人工覆写"的位置。

## 二、五个方向分别补什么

### 方向 1：检索召回率

- **复用**：coverage.py 全部 110 题的 expect_docs 标注（人工已 curated，即"标准相关证据"）+ health72 的 72 题（无标注，仅作链路集，不进检索指标）。
- **新增**：纯函数指标模块 `acceptance/metrics.py`：

| 指标 | 公式 | 数据来源 | 说明 |
|---|---|---|---|
| Recall@K | 命中题数 / 有效题数（排除 `expect_docs=[]` 的 KNOWLEDGE_MISSING） | coverage run JSON 的 hit_rank | K 取 5/10（检索默认 k=10）；命中 = hit_rank ≤ K |
| MRR | mean(1/hit_rank)（未命中计 0），分母同上 | 同上 | |
| top1 命中率 | top1 ∈ expect_docs 的题数 / 有效题数 | 同上 | 补充观察，不设门槛 |
| 失败构成比 | RETRIEVAL_MISS / KNOWLEDGE_MISSING / EVIDENCE_INSUFFICIENT 各占失败侧比例 | classify() 输出 | 归因不丢：调参数前先看病种 |

- **配置对比**：`--k 3/5/10` 参数化检索调用（service 层已支持 MIN/MAX_TOP_K），同一测试集跑多 k 出对比表；Query 改写等其他配置预留同样入口。
- **失败样本分析**：归因字段已在 classify()，报告层按组 × 归因出交叉表，直接指向"是词表缺、切分问题还是排序问题"。

### 方向 2：答案准确率

- **明确立场**：自动化的"答案正确率"在本项目**不可做**——没有也不应伪造标准答案全量集（医疗答案正确性的 gold 需要医学人工）。方案：
  1. **确定性代理指标**（自动、每轮跑）：
     - 完成率（completed / 应完成）分母 = 标注为"库内可答"的题；
     - 证据支持率（自动）= T-16-lite 比值，**标注为诊断趋势**，只与自身历史比，不与 0.85 人工口径混；
     - 来源零编造率（形式化）：展示来源的文档名全部存在于知识库清单（程序可判），逐字引用校验通过率（第 2 段本就有，统计其 pass/retry/fail 分布）。
  2. **人工核验协议**（正式口径，低频）：FR-01 现有 8 样本人工核验流程固化为抽样协议（每轮 completed 样本抽 8 题逐句核对），记录人工支持率——这是唯一允许叫"引用支持率"的数。
- **错误答案归因**：每道 completed 但人工判错的样本按四分类归因（检索失败 / 上下文组装 / Prompt 约束不足 / 生成错误），归因字段进测试集，攒够一批再定向修——这是人工标注动作，工具只提供记录结构。

### 方向 3：幻觉抑制与拒答能力

- **场景集**（新建议题集 `CHAIN_SCENARIOS`，约 20 题，五类）：
  1. 正常可回答（5 题，取 coverage 各组 RETRIEVAL_OK 稳定题）；
  2. 库缺失应拒答（5 题，T-02b 已覆盖 3，再补 2 类：完全无关主题 / 库内主题但无该事实）；
  3. 高风险应拦截（4 题，复用 T-03 形态）；
  4. 边界可答（4 题，取自 72 题中已归因的 G05 类边界题，盯误拒答）；
  5. 证据冲突/不完整（2 题起步，先记录系统实际行为，**不设断言**——当前库无冲突文档对，如实标注为观察项）。
- **指标**（全确定性）：
  - 正确拒答率 = 应拒答题中 outcome=insufficient_evidence 且回答无来源段 / 应拒答题数；
  - **误拒答率** = 边界可答题中 insufficient 的比例（这是本轮新增的最重要的一个数，72 题时期的"B 类 16 题"就是它的人工版）；
  - 无依据断言率 = completed 回答中出现「来源段但 outcome≠completed」或断言式结论无来源支撑的形式化违规数（能程序判的部分；语义部分归人工协议）；
  - 安全拦截保持率 = 门禁 T-03 并入报告，不重复计。
- **红线**：不以"拒答越多越好"为优化目标——报告必须同时展示正确拒答率与误拒答率，两者一起健康才算好。

### 方向 4：Prompt Engineering

- **轻量版本机制**（不做框架）：
  - `acceptance/promptmeta.py`：运行时采集 5 份生产 Prompt + 安全词表的 SHA-256 短哈希，写入每次报告的 meta（**不改 Prompt 存储方式**，纯读取现有常量）；
  - `docs/prompts-CHANGELOG.md`：人工维护的变更日志（日期 + 哈希 + 改了什么 + 动机），与 meta 哈希互相印证；
  - 基线对比时哈希不同 → 报告里提示"Prompt 有变更，指标差异可能来自 Prompt"。
- **基线对比机制**：改 Prompt 后跑同一测试集，`scripts/compare_reports.py`（或并入 report 模块）输出两版 JSON 的逐指标 diff（↑↓→ + 失败样本集合的增删）；收益/副作用从这个 diff 里读，T-14b 电池继续当门禁（已有，不动）。

### 方向 5：自动化测试与评分报告

- **新增 `acceptance/report.py`**：一条命令 `python -m acceptance.report --chat` 串起：
  1. 检索级：coverage 全 8 组（零 LLM）→ 指标计算；
  2. 链路级：CHAIN_SCENARIOS + 门禁用例（真实 LLM）→ 拒答/误拒答/完成率；
  3. 汇总 JSON + Markdown 报告（指标表 / 组×归因交叉表 / 失败样本清单 / 与基线 diff）；
  4. meta：时间戳、git SHA、Prompt 哈希、模型名、索引统计（份数/chunks，从 chroma 读）、测试集版本（health72 冻结号、coverage 组版本）、原始数据文件路径。
- **基线管理**：`acceptance_results/baseline.json` 手动指定某次 run 为基线（拷贝 + 记录原因），后续报告自动对比；换基线必须写原因进报告。
- **诚实性机制**（沿用并强化现状）：blocked 不计 pass；API 挂了整条链路标 blocked；LLM 辅助分数一律带 `llm_assisted: true` 标记字段；报告页脚固定一段口径声明（测试集规模、覆盖范围、不代表真实场景正确率）。

## 四、分阶段实施顺序（每阶段独立可验收）

| 阶段 | 内容 | 新增/修改文件 | 验收标准 |
|---|---|---|---|
| **S1 检索指标层** | `metrics.py` 纯函数（Recall@K/MRR/top1/失败构成）+ coverage 全组一键跑 + 单测锁公式 | `acceptance/metrics.py`（新）、`coverage.py`（加 `--all-groups` 与汇总）、`tests/test_metrics.py`（新，≥8 例含分母边界） | 用 history 上已有 run JSON 重算指标与人工数一致；新跑全组零 LLM 出指标表 |
| **S2 拒答与幻觉指标** | CHAIN_SCENARIOS 题集 + 链路程控 + 正确拒答率/误拒答率/完成率 + T-16-lite 趋势入报告 | `acceptance/chain_quality.py`（新）、`acceptance/scenarios.py`（新）、coverage 题集补 `answerable` 标记 | 场景集 20 题全量真实 LLM 跑通；误拒答率可复现（同输入两轮差 ≤1 题）；指标与 72 题报告历史口径对账（B 类题应 mostly 落"边界可答"） |
| **S3 Prompt 版本与报告整合** | promptmeta 哈希 + Markdown 报告 + 基线 diff | `acceptance/promptmeta.py`（新）、`acceptance/report.py`（新）、`docs/prompts-CHANGELOG.md`（新）、compare 并入 report | 一次 `--chat` 全量产出 JSON+MD；改任一 Prompt 一个字节后重跑，报告 meta 哈希变化且 diff 提示；blocked 语义在全链路保持 |
| **S4 人工核验协议固化** | FR-01 抽样协议文档化 + 人工支持率记录字段 | `docs/FR01人工核验记录.md`（增补流程节）、`fr01.py`（记录结构补 `human_verified` 字段） | 完成一轮 8 样本人工/AI 混合核验并记录（覆盖此前"待人工抽查"遗留） |

**顺序理由**：S1 零 LLM 零风险且所有后续阶段都消费它的指标函数；S2 引入真实 LLM 消耗但产出最高价值的新指标（误拒答率）；S3 把前两段整合成日常闭环；S4 是把唯一"待人工"遗留收口。health72 的 A~S 自动归因作为**观察项**记录在 S2（先把归因字段结构做出来，全自动分类的准确性存疑，不阻塞主线）。

## 五、潜在风险与对策

1. **LLM 额度与波动**：S2/S3 的真实链路消耗 DeepSeek 额度；temp=0 仍有残余不确定性（G05 案例），报告需连跑两轮或标注单轮结果供判读。对策：场景集控制在 ~20 题；大回归（72 题）维持"按需跑"而非常态。
2. **索引漂移**：检索指标与库内容强耦合，扩源/重建后指标跳变≠回归。对策：meta 里记索引统计 + 换库后必须重定基线（报告强制提示）。
3. **指标误用**：Recall@K 是"固定测试集上的测量"，禁止表述为系统正确率（沿用设计文档 6.0 通则，写进报告页脚）。
4. **测试集污染**：health72/coverage 已冻结；新场景集冻结后改题需确认。手工 query 扩展类实验（如 PA-03 的 C 手段）**不得**反向写进测试集。
5. **metric/eval.py 死代码**：建议删除（本方案中 S1 覆盖其全部能力且 store.py 依赖已判不可用），是否删除等你确认。
