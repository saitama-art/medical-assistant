# 登录与用户隔离设计方案（V1.0 增补）

> 状态：设计定稿候选，待用户确认后实施。本文只做设计，不含实现代码。
> 依据：2026-10-23 第一阶段真实代码检查报告（所有文件/行号引用均已核实）。

## 1. 技术选型与取舍

| 决策点 | 结论 | 理由与替代方案 |
|---|---|---|
| 用户/会话/消息存储 | **SQLite**（stdlib `sqlite3`，零新依赖） | 项目当前无 SQL 数据库、requirements 无 ORM；单进程单 worker 部署（session.py 已有此边界约束）；SQLite 与文件持久化共存不冲突。替代：继续纯文件 JSON——查询归属、列表、删除需要全文扫目录，越界风险更高，放弃。 |
| 登录态 | **服务端 Session + HttpOnly Cookie** | 单一后端、单 worker，无跨服务共享凭证的需求；可即时吊销；无需处理 JWT 的密钥管理与吊销名单。JWT 在本项目没有收益且增加复杂度，放弃。 |
| 密码哈希 | **`hashlib.scrypt`**（stdlib，RFC 7914，内存困难型） | 零新依赖（bcrypt/argon2 均需引入二进制依赖）；`secrets` 生成随机盐；存储格式 `scrypt$N$r$p$salt$dk`。 |
| 业务上下文存储 | **复用 [session.py](../../backend/app/medical_agent/session.py)，不改职责** | 见 §5 改造边界。 |
| 公共 RAG 知识库 | **继续共享现有 Chroma**，不建用户级向量库 | 149 份公共 PDF 与任何用户无关；用户数据（会话/消息/资料）一律不进向量库。 |
| `/upload` | 本期改造为**登录 + 管理员白名单**，并修复文件名处理 | 现状无鉴权即可向共享库投毒（见 §7 风险表 R-11/R-12）。用户私有知识库留待后续版本，届时用 Chroma metadata 打 `owner_user_id` 标签 + 检索过滤实现，不拆库。 |

## 2. 数据模型（SQLite）

```sql
CREATE TABLE users (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  username      TEXT NOT NULL UNIQUE COLLATE NOCASE,
  password_hash TEXT NOT NULL,          -- scrypt$N$r$p$salt$dk
  display_name  TEXT NOT NULL DEFAULT '',
  created_at    TEXT NOT NULL,
  last_login_at TEXT
);

CREATE TABLE auth_sessions (            -- 登录态（服务端会话），与业务会话区分
  token      TEXT PRIMARY KEY,          -- secrets.token_urlsafe(32)
  user_id    INTEGER NOT NULL REFERENCES users(id),
  created_at TEXT NOT NULL,
  expires_at TEXT NOT NULL,             -- 滑动过期：空闲 7 天
  revoked    INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE conversations (            -- 业务会话归属表（新增）
  id         TEXT PRIMARY KEY,          -- 服务端 uuid4 生成；即 /agent/chat 的 session_id
  user_id    INTEGER NOT NULL REFERENCES users(id),
  title      TEXT NOT NULL DEFAULT '新的对话',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  deleted    INTEGER NOT NULL DEFAULT 0 -- 软删除
);
CREATE INDEX idx_conv_user ON conversations(user_id, deleted, updated_at);

CREATE TABLE messages (                 -- 全量聊天历史（新增，append-only）
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  conversation_id TEXT NOT NULL REFERENCES conversations(id),
  role            TEXT NOT NULL CHECK(role IN ('user','assistant')),
  content         TEXT NOT NULL,
  created_at      TEXT NOT NULL,
  turn            INTEGER NOT NULL
);
CREATE INDEX idx_msg_conv ON messages(conversation_id, id);
```

关键设计说明：

1. **业务会话 id 改为服务端生成**（`POST /conversations` 返回 uuid4）。前端不再自造 `sess-xxx`。
   现有 client 生成方式的问题不只是归属：它把"标识符生成权"放在不可信端。服务端生成后，归属关系由 `conversations.user_id` 唯一确定。
2. **session.py 的内存/文件存储保留为"运行时上下文窗口"**（最近 5 轮，编排器 N00–N12 专用）；
   `messages` 表是"全量历史"（API 层在 `run_agent` 返回后双写 `raw_question`/`answer_text`）。
   两者关系：session.py 是 messages 表最近 10 条的一个易失缓存，职责不同，不互相替代（对应任务约束 #5）。
3. **消息表不冗余 user_id**：读取消息必须先按 `conversation_id` 查 `conversations` 并校验 `user_id`，
   单点校验、不存在"绕过会话直查消息"的接口。冗余 user_id 会带来双写一致性问题，收益仅为省一次索引查询，不取。
4. **软删除**：`deleted=1` 保留审计与"误删恢复"余地；同时删除 session.py 内存条目与持久化文件（见 §5.3）。

## 3. 认证与授权流程

### 3.1 登录 / 登出 / 当前用户

```
POST /auth/login   {username, password}
  → 查 users；scrypt.verify 常数时间比较
  → 失败：内存计数器（按 username+IP）失败 5 次锁 15 分钟（单 worker 边界内有效，见 §5.4）
  → 成功：写 auth_sessions（token, expires_at=now+7d）；Set-Cookie:
      med_session=<token>; HttpOnly; Path=/; Secure; SameSite=None(dev 跨端口)/Lax(同域部署)
  → 响应体：{id, username, display_name}（不含任何凭证）

POST /auth/logout  → 置 auth_sessions.revoked=1；Set-Cookie 过期
GET  /auth/me      → 无有效 cookie 返回 401；否则返回当前用户信息
```

Cookie 与 CORS 现实约束（前端 React 端口与后端 8000 跨站）：
- 开发态：`SameSite=None; Secure`（现代浏览器对 http://localhost 视为可信源，Secure 可用），
  fetch 必须 `credentials:'include'`；CORS 从 `*` 改为**环境变量白名单**（如 `http://localhost:3000`），
  `allow_credentials=True` 与白名单并存（禁用 `*`+credentials 的非法组合）。
- 生产态：推荐前端 build 由后端/反向代理同源伺服，则 `SameSite=Lax` 即可，CSRF 面最小。

### 3.2 CSRF 防护

1. 自定义头 `X-Requested-With: XMLHttpRequest` 为所有变更类请求必需——它使请求非"简单请求"，
   浏览器强制预检，非白名单 Origin 无法通过；
2. 服务端中间件校验该头存在（缺失 → 403），不依赖 Origin 头做唯一判据；
3. 同域部署时 `SameSite=Lax` 提供第二层兜底。本期不上 double-submit token（复杂度收益不成比例）。

### 3.3 接口授权（资源级校验）

原则（对应任务书）：**前端传来的任何 ID 不可信；当前用户身份只来自 HttpOnly Cookie 解析出的
auth_sessions → user_id；每个涉及具体会话的接口都必须做归属校验。**

统一依赖 `get_current_user`（读 Cookie → 查 auth_sessions → 校验未过期/未吊销 → 返回 user）。
受保护接口分两类：

- **集合级**（/conversations 列表、创建）：只需登录，SQL 天然按 `user_id` 过滤；
- **资源级**（历史、发消息、删除）：先取 conversation，校验 `conv.user_id == current_user.id`，
  失败一律 **403**（不区分"不存在"与"不属于你"，避免通过 404/403 差异探测他人会话是否存在）。

`/agent/chat` 的兼容策略：请求中的 `session_id` 若已存在于 conversations 且属于他人 → 403；
若不存在 → 隐式创建并归属当前用户（保留前端与验收脚本的"直接开聊"体验，且不存在抢注他人数据的风险——他人的 id 必然已存在）。

| 接口 | 状态 | 认证 | 资源授权 |
|---|---|---|---|
| POST /auth/login | 建议新增 | 无（限流保护） | — |
| POST /auth/logout | 建议新增 | 登录 | 吊销自己的会话 |
| GET /auth/me | 建议新增 | 登录 | — |
| POST /conversations | 建议新增 | 登录 | — |
| GET /conversations | 建议新增 | 登录 | 仅返回本人（SQL 过滤） |

## 4. 数据隔离边界

| 数据 | 位置 | 隔离方式 |
|---|---|---|
| 用户资料 | SQLite `users` | 按行隔离；接口只返回本人 |
| 登录态 | SQLite `auth_sessions` | token 不可枚举；HttpOnly 不外泄 |
| 会话列表 | SQLite `conversations` | `user_id` 外键 + 查询过滤 |
| 全量聊天历史 | SQLite `messages` | 只能经归属校验的会话访问 |
| 运行时上下文（最近 5 轮） | session.py 内存 + 可选文件 | 持久化文件按用户子目录存放（§5.3）；本质是易失缓存，泄露面小于历史表 |
| 长期记忆 | 未实现 | 将来按 user_id 行级隔离；不进共享向量库本体 |
| 公共 RAG 知识库 | Chroma（共享） | 只含公共资料；**用户数据一律不入库**；上传接口加管理员门（§6） |
| 用户私有知识库（将来） | 共享 Chroma + metadata `owner_user_id` | 检索侧加 `where owner is None or owner==当前用户` 过滤；不拆库 |

## 5. session.py 改造边界（专项回答）

### 5.1 如何引入用户归属？

**不在 session.py 内做授权。** 归属校验由上层（API 层 + conversations 表）在调用编排器之前完成；
session.py 增加**可选** `owner_user_id` 参数做纵深防御：

- `acquire(sid, owner=None)` / `complete(sid, q, a, got_lock, owner=None)`：签名向后兼容（默认 None = 现状）；
- `owner` 传入时，内存条目与磁盘文件若已存在归属记录且不一致 → 拒绝写入并记日志（不静默混用）；
- orchestrator 调用处不感知 owner（保持其调用不变），由 API 层校验通过后把 owner 透传——为保持编排器签名不变，
  实际落地为：API 层校验归属 → orchestrator 照常调用 → **owner 由 session 模块内的"当前请求上下文"注入**
  （contextvars，FastAPI 依赖注入在入口设置，session.py 内部读取，零签名改动、对编排器与现有测试完全透明）。

### 5.2 职责划分

确认：**session.py 继续只管上下文存取（存什么、截断、锁、TTL、降级），认证与授权全部在上层。**
理由：它的确定性单测（test_session_persist.py）与编排链路 N00/N12 契约已冻结；混入授权会让
"纯存储"测试需要伪造用户体系，破坏现有测试的可维护性（约束 #4/#8）。

### 5.3 文件持久化：冲突、越权、误删

- **目录结构**：`{SESSION_PERSIST_DIR}/{user_id}/{sid}.json`（owner 为空时维持扁平结构，旧文件兼容读取）；
- **ID 冲突**：sid 由服务端 uuid4 生成 + conversations 表主键约束，天然无冲突；`_SAFE_SID` 正则保留；
- **越权读写**：路径组装只允许 (白名单 user_id, 白名单 sid) 两级，contextvars 注入的 owner 与内存条目归属不一致时拒绝；
- **删除**：删除会话 = 软删 conversations 行 + 删除内存条目 + 删 `{user_id}/{sid}.json`，
  三者都按 (user_id, sid) 定位，不存在按裸 sid 扫全局目录的删除路径。

### 5.4 单 worker、会话锁、TTL 在多用户下的影响

- **单 worker 约束不变**：登录态计数、内存限流、contextvars 注入都假定单进程；`WEB_CONCURRENCY>1` 时
  沿用现有降级哲学（会话历史降级），登录功能同样降级提示或拒绝启动，设计文档已记录该边界；
- **会话锁**：粒度仍为 conversation id，多用户只是字典里更多条目，锁竞争面不变；
- **TTL**：30 分钟空闲清理照旧，与归属无关；持久化文件使重启恢复不受 TTL 影响。

### 5.5 文件 vs SQLite 的分工

留在文件/内存：运行时上下文窗口（易失、容量固定、重启可空）。
进入 SQLite：users、auth_sessions、conversations、messages（需要查询、归属、审计的数据）。
判断标准：**需要按用户查询/过滤的一律 SQLite；只是流程内缓存的一律留 session.py。**

### 5.6 不破坏现有链路的保证

1. session.py 公开签名与默认行为不变（owner=None 路径 = 现状）；
2. orchestrator、router、safety、knowledge 子 Agent 零改动；
3. test_session_persist.py 一行不改、必须全绿；
4. 验收 runner 改造为：夹具登录一次获取 cookie，72 题请求带 cookie 重放（runner 本身有 TestClient，成本低）；
5. RAG/检索链路完全不感知用户（公共库），无回归面。

## 6. /upload 专项

现状两个问题（均已核实）：
1. **无鉴权写共享库**：任何人可上传 PDF 入公共向量库 → 知识库投毒 + 隐私内容入库污染他人检索；
2. **文件名直接拼路径**：[main.py:88](../../backend/app/rag/main.py#L88) `os.path.join(UPLOAD_DIR, file.filename)`，
   `filename` 含 `..\` 时可写出目录（Windows 下 `..` 与分隔符均可用）。

处理（本期）：
- 登录 + `users.is_admin=1` 白名单方可上传（管理员即维护公共库的运营者）；
- 文件名净化：仅保留 basename + 白名单字符（`[A-Za-z0-9._\-一-鿿]`），重复名加 uuid 前缀，空名拒绝；
- 上传动作写入 conversations 无关的独立审计日志（谁、何时、文件名、入库 chunk 数），不记录文件内容；
- 检索侧本期不加过滤（管理员上传的视为公共内容）；将来开放用户私有上传时再做 metadata 过滤。

## 7. 安全风险分级与处理优先级

| # | 风险 | 等级 | 现状（已核实） | 处理 |
|---|---|---|---|---|
| R-1 | 未登录访问受保护接口 | 高 | 无保护接口概念，全部裸奔 | §3 全部接口加认证 |
| R-2 | 改会话 ID 访问他人会话 | **极高** | 100% 可利用：无归属概念 | conversations 表 + 403 校验 |
| R-3 | 读历史缺归属校验 | 高 | 无历史接口（历史在 localStorage）；但可通过追问间接套出他人历史 | messages 接口归属校验 |
| R-4 | 向他人会话发消息 | 极高 | 同 R-2 | /agent/chat 归属校验 |
| R-5 | 删除他人会话 | 高（前端侧目前只删 localStorage，后端文件残留） | 后端无删除路径；残留文件长期积累 | DELETE 归属校验 + 级联清 session 文件 |
| R-6 | 前端参数伪造身份 | 高 | 无身份概念，无从伪造；设计须保证永远不从 body/参数取 user_id | get_current_user 唯一身份来源 |
| R-7 | 密码明文/写死代码 | — | 尚不存在密码体系；创建用户走 CLI 脚本 + scrypt | scripts/create_user.py |
| R-8 | Token/Cookie 误用 | 中 | 无凭证体系；风险在于未来实现时用 localStorage 存 token——禁止 | HttpOnly Cookie 方案本身规避 |
| R-9 | 日志泄露隐私/凭证 | 中 | trace 契约已禁用户原文（state.py TraceRecord 注释）；session 日志不落内容；登录日志须只记用户名与结果 | 代码评审清单项 + 测试断言 |
| R-10 | 登录暴力尝试 | 高 | 登录接口将新增，天然引入该面 | 内存限流锁定（§3.1） |
| R-11 | /upload 投毒共享库 | **极高** | 无鉴权（main.py:82） | §6 管理员门 |
| R-12 | /upload 路径穿越 | 高 | filename 直拼路径（main.py:88） | §6 文件名净化 |
| R-13 | CORS `*`+credentials | 中 | main.py:67-73 现网即如此 | 白名单化 |

处理优先级：R-2/R-4（归属校验）→ R-1（认证）→ R-11/R-12（upload）→ R-10 → R-13 → 其余随主改造完成。

## 9. 验收测试方案

前置：临时 SQLite；TestClient；scrypt 参数调低加速；两个用户 A/B 由夹具创建。

| # | 用例 | 步骤 | 预期 |
|---|---|---|---|
