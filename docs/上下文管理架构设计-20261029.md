## 1. 现状总结

### 1.1 一轮请求的完整上下文链路（代码证据）

```
POST /agent/chat（main.py:85）
  │  登录/CSRF/session 归属（claim_or_verify）；req.question 原样传入
  ▼
N00 run_agent 入口（orchestrator.py:77）
  │  新建 AgentState（raw_question=原文，永不改写）
  │  session.acquire(session_id) ── 内存轨历史（deque 5 轮，含 truncated 标记）
  │  context_engineering.begin_turn(state) ── owner 非空时改读 SQLite 全量：
  │      conversations.list_messages（≤500 条）
  │      load_pending_tasks（agent_tasks 表，followup 带 7 天 TTL）
  │      load_facts（user_facts 表）
  │  refresh_context → build_context 组装 ContextPackage（token 预算 3000）
  ▼
N01 急症规则（原始问题，safety 词表，0 LLM）
  ▼
N02 上下文补全（仅当 has_reference/has_followup_lead 且历史非空）
  │  输入：format_history(context_package)（预算筛选后的 SQLite 历史）
  │        + M4 待续任务锚点（用户原文）+ resolved_question

  │        no-op 三态；失败 → RESOLUTION_FAILED（不谎称历史丢失）
  ▼
N03 急症规则复査（改写后文本，与 N01 取强者）
  ▼
N04 意图识别（intent.py，输入仅 resolved_question 单句，无历史）
  │  unresolved=missing_input/context_required 不阻断可回答类别，
  │  仅登记 M4 followup 待续任务（context_engineering.register_followup）
  ▼
N05 确定性路由表（router.decide_route，7 条优先级，无模型判断）
  ▼
分支：CHITCHAT/UNCLASSIFIABLE → 固定文案；TRIAGE → 固定指引；
      DAILY → daily.py（LLM，输入=内存轨最近 6 条消息+本轮问题）；
      KNOWLEDGE → 委派

N06 委派（delegate.py → task_spec.py）
  │  TaskSpec.inputs = {question}（补全后独立问题）——不传会话历史（契约级隔离）

  ▼

  ▼
N09 回边（k+2 扩大候选，最多 1 次）
  ▼
```

### 1.2 上下文信息的现有载体（已实现，结构化程度较好）

| 信息类别 | 载体 | 持久化 | 进模型时的形态 |
|---|---|---|---|
| 原始问题 | `AgentState.raw_question` | messages 表（user 行） | N01/N04a 直接用原文 |
| 独立问题 | `resolved_question` | 不落库（仅 API 调试字段） | N02 产物，N04/N07/N08/N10 的输入 |
| 对话历史 | 双轨：内存 deque（5 轮，剥离版）/ SQLite（≤500 条，完整版） | 两轨都存 | 拍平为「用户：…/助手：…」文本 |
| 待续任务 | `TaskRecord`（agent_tasks 表） | SQLite | JSON 摘要进 ContextPackage 必需段 |
| 用户事实 | `StructuredFact`（user_facts 表，带 source_message_id） | SQLite | JSON 摘要进必需段 |
| 检索证据 | `RetrievedChunk`（仅运行时） | 不持久化 | 拼成一段 `{context}` 文本 |
| 系统指令/安全约束 | 各模块 Prompt 常量 | 代码 | system role |
| 任务状态 | `AgentState`（单请求生命周期） | trace 不落库 | 不进模型 |

### 1.3 已实现的关键能力（不要推倒）

- **子 Agent 上下文隔离是契约级的**（task_spec.py）：inputs 仅 question、
  指纹校验、Permit 单次消费、结果验收含"来源必须出自检索""失败不得带部分回答"。
- **改写保真的程序校验**（resolver.py）：否定词丢失即拒绝、no-op 不猜、
  硬指代词自含采信被否决。
- **历史写回的语义保留**（session.py `_strip_answer_for_history`）：
  剥离组装件但保留风险提示与紧急文案。
- **任务/事实的归属与溯源**：persist_turn_context 同事务校验来源消息归属，
  跨用户写入硬拒绝。
- **预算体系**：请求 45s 硬上限 + 环节预算 + N08/N10 前证据 token 估算检查
  （EVIDENCE_CONTEXT_TOKEN_BUDGET=12000，超限显式失败）。

## 2. 问题清单

### 2.1 有代码证据的问题

**P1（高）：SQLite 历史轨未剥离组装件，S1-D3 的收益在真实路径上被绕过**
- 证据链：`main.py:122` 把 `state.answer_text`（N11 组装后的完整版，含
  【参考来源】与免责声明）原样落库 → `begin_turn`（context_engineering.py:636）
  经 `list_messages` 读全量 → `resolver.py:74-76` 的 format_history 消费
  `context_package.recent_history`（即 SQLite 轨）。
- `_strip_answer_for_history`（session.py:286）只作用于内存轨；登录后
  N02 实际消费的是 SQLite 轨。
- 后果：① N02 改写 prompt 被来源段/免责声明膨胀（S1-D3 当初要解决的问题
  仍在）；② ContextPackage 的 3000 token 历史预算被组装件消耗，挤占真实
  对话内容，长回答多的会话更早触发历史省略。
- **修复边界（评审条件 1）**：展示与存储解耦——N11 assemble 的运行时输出
  （回答+来源+免责声明）**不变**，API 响应字段与前端渲染不受影响；修复只改
  落库内容与读取进上下文的内容。已有历史记录**不做数据迁移**：读取侧做
  幂等剥离（含组装件的旧记录剥离、不含的新记录原样通过），新旧格式混合的
  会话读取结果一致；剥离规则单一出处（session.py 逻辑上移 conversations 层）。

**P2（高，潜伏数据正确性）：`list_messages` 取最早 500 条而非最近 500 条**
- 证据：conversations.py:122-125 `ORDER BY id LIMIT 500`——升序取头部，
  即最旧 500 条。会话超过约 250 轮后，上下文"定格"在会话开头，最近的历史
  永远进不了窗。
- 待验证：生产数据是否已有会话接近该量级（当前测试库最大会话轮数待查；
  修复本身是一行排序反转，不依赖该统计）。

**P3（中）：双轨历史口径并存，语义不一致**
- 内存轨（session.py）：5 轮、剥离版、有 truncated→MISSING 显式标记；
  SQLite 轨：≤500 条（最旧）、完整版、**无截断标记**（到顶静默丢失）。
- 消费分轨：N02 走 SQLite 轨（format_history 优先 context_package）；
  daily 走内存轨（daily.py:38-43 `state.history[-6:]`）；turn_id 计数走
  内存轨（orchestrator.py:93）；N02 触发判定看内存轨是否非空
  （orchestrator.py:128 `state.context_history`——实为 SQLite 轨，口径混用）。
- 后果：同一轮请求里"历史"一词有两套语义；truncated 保护只对内存轨生效。

**P4（中）：判定与生成的证据口径不一致，证据进模型无选择器**
- judge 用 `_dedupe_for_judge` 聚焦子集（每文档≤2 段，回退全量）；
  generate 用**全量 10 段**（service.py:522-527）。
- `EVIDENCE_CONTEXT_TOKEN_BUDGET` 只是事前超限即失败的检查
  （knowledge.py:137-153），不是"在预算内选哪些段"的选择器。
- 证据在 prompt 中就是一段 "\n\n" 拼接文本：无 per-chunk 配额、无来源标签
  随文（模型不知道哪段来自哪个文档第几页——来源展示靠 metadata 另走，
  但**判定/生成时模型无法把句子归属到具体文档页**，引用质量靠第 2 段
  逐字校验兜底）。

**P5（中，已记录未实现）：改写保真只有否定词程序校验**
- 时间范围、数值/单位、比较关系、人群限定在改写中丢失无程序校验
  （进度文档 2026-10-25 CS-19 观察项已记录）。resolver prompt 规则 3/4
  覆盖了实体与否定/限定，但程序侧只校验否定词。

**P6（低）：证据在 prompt 中的角色位置不一致**
- judge：证据在 user 段（service.py:393-399）；generate：证据在 system 段
  （chain.py:144-146）。无功能故障，但违反"同类信息稳定位置"原则
  （见 §3 原则 2），跨节点对比与缓存友好性受损。

**P7（边界，非缺陷）：N04 分类器无历史**
- 分类只凭 resolved_question 单句。这是刻意架构（N02 先补全），代价是
  触发器漏网的短句缺少分类语境。记录为已知边界，不建议本轮改。

### 2.2 待验证风险（无充分证据，不下结论）

- 长会话（>250 轮）下 P2 是否已造成真实用户影响——待统计 messages 表。
- `estimate_tokens` 启发式（中文 1 字=1 token）相对真实 tokenizer 的
  高估率——影响预算利用率，待抽样实测。
- daily 路径取内存轨最近 6 条（3 轮），对"对话回顾"类问题是否过短
  （「我们今天聊了什么」在 >3 轮会话里只能回顾最近 3 轮）——待实测。

## 3. 设计原则：借鉴 Transformer 输入机制，不混淆两层机制

Transformer 的输入处理对**应用层**有启发的，是以下六条性质；注意力、
位置编码、KV-cache 等模型内部机制**不借鉴、不模拟**（本层保持模型无关，
换模型时上下文层零改动——2026-10-28 DeepSeek→Kimi 切换已实证该价值）。

**原则 1：模型只见 token 序列，结构全靠应用层显式表达。**
每类信息进 prompt 必须有稳定、可解析的边界标记（角色/段落标签），
不得混成无法追踪来源的文本。现状已部分做到（结构化载体齐全），
缺口在"进 prompt 前的最后一拍被拍平"——目标架构用 ContextManifest
把拍平前的结构保留下来（§4-8）。

**原则 2：同语义的输入出现在稳定位置。**
系统指令/安全约束恒在 system 首部；本轮问题恒在 user 尾部；证据的
角色与标签格式跨节点统一（修 P6）。位置稳定 = 行为可预期 + 前缀可复用。

**原则 3：上下文窗口是稀缺资源，按类别分配预算，准入需校验。**
token 预算从"总量估算 + 超限失败"升级为"类别配额 + 选择器"：
必需内容（当前问题/任务/事实/安全约束）永远优先；历史与证据各有
配额与选择规则；被省略项必须可见（omitted 计数已有，扩展到全类别）。
注意力无差别作用于全部 token——塞进去的每一段都在竞争模型的注意力，
"塞得下就塞"等于主动稀释关键指令（CS-09 同文档刷屏带偏判定是实证）。

**原则 4：模型无状态，跨轮连续性由应用层显式重建。**
任务、事实、锚点必须是一等公民的结构化记录（已有 TaskRecord/
StructuredFact），不得依赖"模型大概记得"。旧事实标
historical_unconfirmed 不自动当新输入（已有），保留。

**原则 5：对逐字 token 敏感 ⇒ 语义保真用程序校验，不指望模型自觉。**
已有 dropped_negation 是范例；扩展到时间/数值/单位（P5）。校验规则
宁严勿宽，校验不过走澄清，不猜。

**原则 6：送入模型的内容必须可回放、可审计。**
Transformer 每次调用都是完整重放——应用层的对应物是：每次模型调用
的输入构成（哪些轮次/事实/证据、各自预算、省略原因）落成
ContextManifest 进 trace。没有这个，一切上下文优化都无法归因
（评估体系 S4d 的"这轮改了什么"诉求在上下文层的对应）。

**明确不做的**：不实现/模拟 Attention 机制；不做与特定模型 tokenizer
的对齐（保留保守启发式估算，误差率列为待验证项）；不引入位置编码、
滑窗注意力等模型层概念到应用层命名与文档。

## 4. 目标架构

### 4.1 总体流程图（目标态，改动处标 ★）

```
原始输入（main.py，保留）
  │
  ▼
① 输入受理与约束提取：N00 校验 + N01/N03 安全规则（保留）
  │     raw_question 永不改写；resolved_question 是衍生副本
  ▼
② 历史服务（★收敛）：SQLite 为唯一事实来源
  │     写入即剥离组装件（★P1）；读取取最近 N 条（★P2）
  │     session.py 退化为锁/并发控制层，不再承担历史内容
  ▼
③ 上下文组装器（build_context 升级）
  │     类别配额：必需(问题/任务/事实/冲突) > 历史 > 证据
  │     历史选择：最新轮优先 + 相关性补充（保留）+ 省略计数
  ▼
④ 改写与保真校验（resolver + ★时间/数值/单位校验扩展 P5）
  ▼
⑤ 意图/路由（保留；分类器无历史为既定边界 P7）
  ▼
⑥ 证据管理（★统一选择器）：检索 → 去重/配额/排序 → 已选证据集
  │     judge 与 generate 消费同一份（★P4）；证据角色位置统一（★P6）
  ▼
⑦ 子 Agent 隔离（task_spec，保留不动）
  ▼
⑧ ContextManifest（★新增）：每次模型调用的输入构成清单 → trace
  │     （每段来源/类别/token 估算/省略项与原因）
  ▼
终态收口与写回（finalize + ②的写入路径，保留 + ★剥离上移）
```

### 4.2 模块职责与输入输出（与现有代码的对应）

| # | 模块 | 现状对应 | 处置 | 职责（目标态） |
|---|---|---|---|---|
| ① | 输入受理 | main.py / orchestrator N00-N01 | 保留 | 接收原文、归属校验、安全拦截 |
| ② | 历史服务 | conversations.py + session.py | **调整** | SQLite 单一事实来源；写入剥离组装件；读最近 N 条；session.py 只留锁与并发降级 |
| ③ | 上下文组装 | context_engineering.build_context | **调整** | 类别配额分配；历史/证据选择；预算硬失败保留 |
| ④ | 改写与校验 | resolver.py | **调整** | 改写 + 否定/时间/数值/单位程序校验 |
| ⑤ | 意图与路由 | intent.py / router.py | 保留 | 不改 |
| ⑥ | 证据管理 | rag/service.py | **调整** | 统一证据选择器（去重+配额+来源标签随文）；judge/generate 同一输入 |
| ⑦ | 子 Agent 契约 | task_spec.py | 保留 | 不改（已是目标态） |
| ⑧ | 完整性追踪 | （新）ContextManifest | **新增** | 每次模型调用的输入构成审计，落 trace |

不为凑数新增的模块：摘要压缩器（现阶段证据不足，见 §4.4 决策）、
独立"记忆管理器"（事实表已承担）。

### 4.3 关键数据结构建议（设计级，非实现）

**ContextManifest（新增，运行时 + trace；最小版先行，只观测不改行为）**

每次模型调用必须记录（字段即验收标准，评审条件 3）：
- **调用标识**：call_id、节点（N02/N04/N08/N10/daily）、任务引用
  （task_id / spec_id，无则为空）、执行结果（NodeStatus / termination）。
- **所用历史**：消息 id 列表（messages 表主键）+ 轮次计数 + 省略计数与
  原因（budget / relevance）；当前无摘要机制，若未来引入则记摘要 id 而非原文。
- **所用检索证据**：每段的 (document, page) 引用 + 内容哈希前 8 位 + 在窗
  顺序；被排除项及原因（dedupe / budget）。
- **输入构成与 token**：分段估算（system / 历史 / 证据 / 问题）与总量。
- **隐私纪律（医疗项目硬性）**：只存 ID、引用、哈希、长度与计数，
  **不复制用户/患者原文**（与 TraceRecord 既有"detail 不含原文"纪律一致）；
  manifest 只进运行时 trace——不落 SQLite、不经 API 返回、不进前端；
  评估工具离线读取 run JSON，访问面即本机仓库与本地报告。

**已选证据集 EvidenceSelection（新增，运行时）**
- 字段：chunks（经过去重/配额/排序）、每 chunk 的来源标签
  （文档+页，随文注入 prompt）、选择规则版本、被排除项及原因。
- judge/generate/来源展示三方消费同一份，口径唯一。

**历史写入形态（调整）**
- messages 表结构不变（不加列、不迁移）；写入的 assistant content
  存剥离组装件后的正文（剥离规则从 session.py 上移 conversations 层，
  单一出处）。展示层需要的来源列表本就由响应字段单独返回，不依赖
  消息正文。

### 4.4 数据生命周期与存储边界

| 数据 | 运行时 | 持久化 | 备注 |
|---|---|---|---|
| 原始问题/回答正文 | AgentState | messages（剥离组装件★） | 回答的完整版仅存于 API 响应 |
| resolved_question | AgentState | 不落库（现状保留） | API 调试字段保留 |
| 任务/事实 | AgentState + SQLite | agent_tasks / user_facts | followup 7 天 TTL 保留 |
| 证据 chunks | AgentState | 不持久化 | 来源引用进 trace |
| ContextManifest | trace | 不落库 | 评估经 run JSON 取数 |
| trace/tool_calls | AgentState | 不落库 | 现状保留 |

**摘要压缩的决策（任务书 §四.2 要求对比，此处给结论）**：
现阶段**不引入**历史摘要。理由：医疗场景的否定/时间/单位/限定语在
摘要中丢失的风险不可控（V1 既定决策，2026-10-27 已记录）；当前 5 轮
内存窗口/SQLite 全量的矛盾应先用 P1/P2/P3 的确定性手段解决。摘要只在
将来出现"长会话高频追问"的真实诉求时再评估，且必须带原句索引可回溯。
各方案对比：最近 N 轮（简单、丢早期关键信息）/ 检索相关历史（词项匹配
已有，语义检索待验证）/ 摘要（信息丢失不可控，否）/ 任务最小上下文
（已有 TaskRecord，保）/ 结构化事实（已有 StructuredFact，保）。

### 4.5 风险与处理

| 风险 | 处理 |
|---|---|
| 历史剥离规则改变旧数据的读取口径 | 读取侧做幂等剥离（对已含/不含组装件的旧数据都安全），不迁移旧数据 |
| 证据选择器改变 judge/generate 输入，验收基线漂移 | 按 prompts-CHANGELOG 登记指纹；全量验收重跑后才允许任命新基线 |
| list_messages 排序反转改变长会话行为 | 行为变化即修复目的本身；补长会话单测 |
| ContextManifest 膨胀 trace | 只存引用/计数；trace 本就限运行时 |
| 双轨收敛影响 daily/turn_id 口径 | 收敛排在阶段 3，依赖阶段 1/2 稳定；daily 改读统一历史服务 |

## 5. 渐进式改造计划

按用户确认的四阶段执行，不增加新的大型模块。

**阶段 1（修复 P1/P2 + 回归测试）**
1. P1：历史写回剥离组装件上移到 conversations 层；读取侧幂等兼容旧数据，
   不做数据迁移；展示侧 N11 组装与 API 响应不变。
2. P2：list_messages 改为取最近 N 条（DESC LIMIT 后反转回时间升序）。
- **P1 双侧验收（评审条件 1）**：
  ① 展示侧——页面仍展示完整回答、参考来源、免责声明（容器实测，
  响应字段齐全）；② 上下文侧——N02 读取的历史不含来源段/免责声明
  （单测断言 + 实测对比改写 prompt 的历史段长度）；③ 兼容性——
  含组装件的旧记录与不含的新记录混合的会话，读取结果一致（单测）。
- **P2 边界测试（评审条件 2）**：消息数 499 / 500 / 501 / 600 四档——
  >500 时返回最新 500 条且按时间升序、内容与原序列尾部一致；
  =500 全量返回；<500 全量返回；归属校验不受影响（单测）。
- 回归闸：全量单测绿；门禁 T-12/T-13 多轮用例不回归；本阶段不改 Prompt，
  CHANGELOG 指纹应无变化（若有变化说明改错了范围）。

**阶段 2（最小版 ContextManifest，先观察真实输入）**
3. 按 §4.3 字段清单落 trace——零行为变化，只记录不改变任何模型输入；
   estimate_tokens 抽样对账真实 tokenizer（只出误差报告，不改算法）。
- 验收：每次模型调用的 trace 带完整 manifest（字段完整性单测）；
  **隐私抽查——trace 中无用户/患者原文**（单测断言 + 人工抽查 run JSON）；
  输出 token 估算误差报告。

**阶段 3（统一 judge/generate 证据选择口径）**
4. 证据选择器统一：去重 + 配额 + 来源标签随文，judge 与 generate 消费
   同一份已选证据；P6 证据角色位置随本阶段一并统一（建议证据放 user 段，
   system 只留指令，符合原则 2）。
- 验收：两节点输入证据逐字节一致的单测；全量真实验收（72 题 + 场景集 +
  门禁）重跑不劣于基线；CHANGELOG 登记指纹变化。

**阶段 4（依观测结果处理保真与压缩策略）**
5. 依阶段 2 的观测数据决定：P5 改写保真校验扩展（时间/数值/单位/比较
   关系）、类别配额分配器、P3 双轨收敛是否启动；摘要压缩默认仍不引入
  （§4.4），除非观测证明 token 压力主要来自长历史。
- 验收：CS-19 类用例入库；构造丢限定语的对抗改写用例全被拒；
  配额省略计数可查。

每阶段独立可交付、独立回滚；阶段 3 依赖阶段 1/2 稳定运行后再动。

## 7. 第一阶段最值得解决的 1~3 个问题

1. **P1：SQLite 历史未剥离组装件**——直接影响每一轮追问的改写质量与
   token 效率，修复面小（写入侧上移 + 读取幂等），收益立竿见影。
2. **P2：list_messages 取最旧 500 条**——潜伏的数据正确性问题，
   修复一行；长会话用户正在"看着助手忘记最近聊的内容"。
3. **阶段 2 的 ContextManifest（观测）**——P4/P5 及一切后续上下文优化
   都缺"模型到底看到了什么"的可归因数据；观测先行、零行为风险，
   为阶段 3/4 提供验收手段。
