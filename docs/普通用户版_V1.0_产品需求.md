## 2. 现状基线

> 本节陈述**可验证的现状**，用于判断功能可行性。它**不是需求**。结论来自 `docs/汇总.md` 的实测盘点，并已更正其中一处环境误判。

### 2.1 已有且可用

| 能力 | 现状 |
|:---|:---|
| 向量知识库 | `backend/chroma_db`，集合 `langchain`，**329 个 chunk**，来源为 **11 份处方药说明书 PDF** |
| 向量检索与来源元数据 | `backend/app/rag/store.py` 的检索入口实测可用；来源元数据取自文档真实 metadata，未造假 |
| RAG 端到端问答 | `backend/app/rag/chain.py` 链路在项目实际运行环境（conda 环境 `ai_agent`）中可用，`/chat/stream` 实测返回 200 |
| 前端界面 | 单页聊天界面 + PDF 上传，可运行 |

> **更正说明：** `docs/汇总.md` 中「`langchain_chroma` 未安装、主链路不可运行」的结论，是在**错误的 Python 解释器**（base 环境）下验证得到的误判——项目实际运行在 conda 环境 `ai_agent`，依赖完整。该文档尚未修订，见第 10 节待确认 11。

### 2.2 当前不存在

| 能力 | 现状 |
|:---|:---|
| 主 Agent（意图识别 / 路由 / 工具编排） | **不存在**。`backend/app/agent/` 下 18 个文件全部是与医疗无关的学习演示 |
| 证据充分性判定 | **不存在**。检索永远返回结果，系统无法判断"库里到底有没有依据" |
| 紧急风险识别 | **不存在** |
| 一般就医指引 | **不存在** |
| 多轮上下文 | **不存在**。后端按单轮问题接收，前端不保留上下文 |
| 引用展示 | **不存在**。前端只渲染回答正文 |

### 2.3 知识库覆盖度（实测）

| 业务类别 | 覆盖情况 | 实测说明 |
|:---|:---|:---|
| 药品信息（说明书） | ✅ 覆盖 | 11 份说明书，命中距离约 0.53 |
| 常见健康知识 | ❌ 无 | 返回无关说明书片段（距离 0.89–1.10） |
| 疾病科普 | ⚠️ 极有限 | 仅在药品适应症范围内 |
| 检查指标基础解释 | ❌ 无 | 无独立资料 |
| 一般性就医指引 | ❌ 无 | 无任何资料 |

实测存在一条可用区分带：库内有覆盖的问题距离集中在 **0.53–0.80**，库内基本没有的问题在 **0.89–1.10**，约在 **0.85** 附近可分。但该阈值只是单点实测初值，**必须用测试集校准后才能作为验收依据**。

### 2.4 这条基线对 V1.0 的直接含义

「健康知识问答」这个能力本身现在就可以做，但**能回答什么，受限于知识库里有什么**。当前能支撑的只有药品说明书类问题；其余类别需要先补充资料（见第 10 节待确认 1、2）。这直接决定了第 7 节的优先级划分。

## 3. 产品定位

### 3.1 目标人群

**非医疗专业人员的普通用户**：有日常健康疑问，但不具备判断医学信息可信度的能力，也没有稳定的专业咨询渠道。

**不在本版本服务范围：** 医学生、医学研究人员、临床医生（属整体需求的第二、第三阶段用户）。

### 3.2 核心痛点

| 编号 | 痛点 | 典型表现 |
|:---|:---|:---|
| P-1 | 网上健康信息真假难辨 | 同一问题搜到互相矛盾的说法，无法判断谁对 |
| P-2 | 通用 AI 在健康问题上会"编" | 给出看起来合理、但没有出处、甚至错误的结论 |
| P-3 | 看不懂专业材料 | 药品说明书、化验单上的指标看不懂 |
| P-4 | 不知道该找谁 | 出现症状后不知道挂什么科、该不该去医院 |
| P-5 | 危险情况被忽略 | 把需要急诊的症状当成小毛病，先来问 AI |

其中 **P-2 和 P-5 是本版本必须正面处理的痛点**，也是本产品与"套壳通用大模型"的根本区别。

### 3.3 使用场景

| 编号 | 场景 | 用户想得到 |
|:---|:---|:---|
| S-1 | 查药 | 某个药是治什么的、怎么用、有什么不良反应 |
| S-2 | 查病 | 某个症状或疾病的一般知识 |
| S-3 | 看指标 | 某项检查指标是什么意思、参考范围是多少 |
| S-4 | 找方向 | 出现某种不适，该去哪个科室、要不要就医 |
| S-5 | 求助急症 | 出现疑似危险症状时，当下该怎么做 |

**V1.0 的主要场景是 S-1、S-4、S-5。** S-2、S-3 受知识库覆盖限制，见第 7 节。

### 3.4 V1.0 产品目标

> 在**有证据、有出处、有安全兜底**的前提下，为普通用户提供一个可用的健康知识问答入口。

核心不是"回答得多"，而是三件事：

1. **有依据就答**，并给出真实可追溯的来源；
2. **没依据就说没依据**，不编造；
3. **有危险就拦住**，优先引导线下就医。

### 3.5 功能边界

- 回答基于**已入库资料**，不依赖模型自身记忆输出医学结论。
- 覆盖知识库已有资料的问题类型；无资料时明确说明，而不是勉强作答。
- 不提供个体化诊断、处方和用药剂量。
- 只服务普通用户的健康知识需求，不含专业医学检索。

## 4. 功能需求

### 4.1 功能清单

| 编号 | 功能 | 优先级 | 依赖 | 对应整体需求 |
|:---|:---|:---|:---|:---|
| FR-01 | 基于知识库证据的健康问答 | P0 | 现有 RAG 链路 | F2、F3、U1 |
| FR-02 | 证据充分性判定与无依据处理 | P0 | **需新增** | F2、F6、U5 |
| FR-03 | 知识来源展示 | P0 | 现有来源元数据 | F6、U2、U3 |
| FR-04 | 一般就医指引与紧急风险提示 | P0 | **需新增**（规则） | F5、F6、U6 |
| FR-05 | 普通对话与问题意图识别 | P0 | **需新增** | F4、B4 |
| FR-06 | 多轮对话与上下文管理 | P0（最小形态） | **需新增** | F7、U4 |
| FR-07 | 资料上传与处理状态反馈 | P0 | 现有上传能力 | F1、U7 |
| FR-08 | 异常处理与回答限制 | P0 | **需新增** | F3、F6、B7 |
| FR-09 | 基础健康指标解释 | **P1**（数据依赖） | 依赖知识库扩充 | F2、S-3 |

### 4.2 功能定义

#### FR-01 基于知识库证据的健康问答

- **描述：** 用户用自然语言提出健康问题，系统从知识库检索相关证据，基于证据生成回答。
- **输入：** 一条自然语言问题。
- **输出：** 一段回答；其中的医学结论必须能对应到检索到的证据片段。
- **边界：**
  - 只在知识库有足够依据时才给出实质性结论；
  - 回答不超出检索证据的范围；
  - 不使用模型自身记忆补全缺失的医学事实。
- **现状：** 链路已存在，但缺少「证据是否足够」的判定（见 FR-02）。当前对任何问题都会取回片段并作答。

#### FR-02 证据充分性判定与无依据处理

- **描述：** 在生成回答之前，先判断检索到的内容是否真的构成依据；不构成时，**不把无关片段交给模型作答**。
- **输入：** 检索结果及其相关性度量。
- **输出：** 「证据充分」或「证据不足」二值信号；证据不足时给出固定应答。
- **边界：**
  - 判定必须发生在**生成之前**，而不是让模型自己说"我不确定"；
  - 判定环节失败时必须**保守降级**为"证据不足"，不得降级为"正常作答"；
  - "证据不足"的应答文本中不得出现任何具体医学结论。
- **现状：** 完全缺失。**这是 V1.0 最关键的待建能力**——没有它，FR-01 会直接退化为"用无关片段编造答案"。
- **说明：** 判定的实现方式（阈值、模型判别或其他）属技术方案，本文不规定；本文只要求「生成前判定 + 失败时保守降级」。

#### FR-03 知识来源展示

- **描述：** 回答中展示该结论所依据的真实来源。
- **输入：** 检索链路返回的来源元数据。
- **输出：** 至少包含文档名称；源文件可提供时包含页码或章节；可查看命中的原文片段。
- **边界：**
  - 来源必须来自检索链路的真实元数据，**不允许由模型生成**文档名或页码；
  - 无法确定页码时，宁可只显示文档名，不得推测；
  - 来源要与回答中的**具体结论**对应，而不是把全部检索结果堆在末尾。
- **现状：** 后端已返回真实来源元数据；前端未展示。

#### FR-04 一般就医指引与紧急风险提示

- **描述：** 识别用户问题中的紧急风险信号并给出就医引导；对"该去哪个科/要不要去医院"一类问题给出一般性指引。
- **输入：** 用户问题文本（含多轮上下文）。
- **输出：**
  - 命中紧急信号：明确、简短的急救/急诊提示；
  - 一般就医指引：不针对个体诊断的通用建议。
- **边界：**
  - 紧急提示**优先级最高**，先于常规问答返回；
  - 紧急提示中**不得**给出病因判断或用药建议；
  - 紧急判定应为确定性规则，保证可复现、可审计；
  - 不得因为"知识库没有资料"而跳过紧急提示。
- **现状：** 完全缺失。
- **待确认：** 非紧急情境下是否必须给出**具体科室**建议（涉及准确性与责任），见第 10 节待确认 9。

#### FR-05 普通对话与问题意图识别

- **描述：** 识别用户输入属于哪一类，并据此决定处理路径。
- **输入：** 当前问题 + 必要的会话上下文。
- **输出：** 问题类别 + 选定处理路径。类别集合为：知识问答 / 就医指引 / 紧急提示 / 闲聊或无关 / 无法处理。
- **边界：**
  - 简单问题直接处理，不进入无意义的多轮调用；
  - 无法归类时按"无法处理"如实回应，不猜测用户意图；
  - 类别判定结果必须可被记录（见 AG-07）。
- **现状：** 缺失。当前所有输入都走同一条 RAG 链路。

#### FR-06 多轮对话与上下文管理

- **描述：** 在同一会话内，用户可以用"它""这个药""那副作用呢"等指代继续追问。
- **输入：** 按时间顺序排列的会话消息。
- **输出：** 结合上下文补全后的完整问题，以及对应的回答。
- **边界：**
  - 上下文只用于**补全用户的问题表述**，不用于替代证据；
  - 不同会话之间的数据不得串用；
  - 上下文超出保留范围时，必须明确告知用户"较早的对话已不再保留"，不得静默丢弃。
- **现状：** 缺失。前端不保留上下文，后端按单轮问题接收。
- **V1.0 范围：** 仅同一会话内保留最近若干轮（轮数待确认，见第 10 节待确认 6）。**跨会话历史持久化、多设备同步、用户账号不在本版本内。**

#### FR-07 资料上传与处理状态反馈

- **描述：** 用户上传资料以扩充知识库，并能看到处理结果。
- **输入：** 文档文件（V1.0 支持的格式待确认，现有实现为 PDF）。
- **输出：** 处理状态（处理中 / 成功 / 失败）与可读的失败原因。
- **边界：**
  - 解析失败的资料**不得**被标记为成功；
  - 失败原因要能被非技术用户看懂，且不暴露内部堆栈或路径；
  - 处理失败不得留下"半入库"状态（要么可检索，要么明确失败且不产生可检索内容）。
- **现状：** 上传接口已有；处理状态反馈的完整性未经验收。
- **V1.0 范围：** 重复文件检测、删除能力**暂不纳入**，见第 7.3 节。

#### FR-08 异常处理与回答限制

- **描述：** 在模型、检索或工具异常时，给出明确、安全的反馈，而不是错误答案或空白。
- **输入：** 各环节的异常信号。
- **输出：** 用户可理解的提示。
- **边界：**
  - **任何异常都不得降级为"编造一个回答"**；
  - 提示中不得出现堆栈、密钥、内部路径或模型配置；
  - 连续失败时给出重试建议；
  - "检索返回空结果"与"检索失败"必须给用户不同的提示。
- **现状：** 部分环节有基础捕获，未系统化。

#### FR-09 基础健康指标解释

- **描述：** 解释常见检查指标的含义与参考区间。
- **状态：** **P1，且存在前置条件。**
- **原因：** 当前知识库完全没有指标类资料。实测该类问题会命中无关的药品说明书，而命中的文档中**并不包含所问的答案**——属于"看起来检索到了，实际答不了"。在资料补齐之前本功能无法验收，**因此不列为 P0**。
- **待确认：** 资料是否补充、参考区间的来源与责任归属，见第 10 节待确认 4。

## 5. 主 Agent 需求

V1.0 采用**单个受控 Agent**，不引入多 Agent。理由：V1.0 的问题类别有限（第 3.3 节的五个场景），且整体需求已明确第一阶段「不把复杂 Multi-Agent 作为前置条件」。

### 5.1 职责边界

**由 Agent 负责（不封装为工具）：**

- 判断问题类别（FR-05）；
- 决定处理路径：直接回应 / 走知识库检索 / 走就医指引 / 走紧急提示 / 拒答并引导；
- 组织最终回答、来源展示与风险提示；
- 控制执行轮数、超时与调用预算。

**理由：** 这些是编排决策本身。若把它们也做成"工具"，模型需要先决定"要不要做决定"，会产生无意义的额外轮次，与整体需求 F4「简单问题不做无意义的多轮调用」相冲突。

**由工具承担：**

| 工具 | 用途 | V1.0 是否必需 |
|:---|:---|:---|
| 知识库检索 | 取回证据与来源 | 必需（FR-01） |
| 紧急风险检查 | 命中紧急信号 | 必需（FR-04） |
| 指标参考区间查询 | 指标解释 | 否（依赖 FR-09 的数据前提） |
| 文档片段详情 | 查看命中原文 | 视 FR-03 的展示粒度决定 |

工具的具体名称、参数与返回结构属接口设计，不在本文规定。

### 5.2 Agent 需求条目

| 编号 | 需求 | 说明 |
|:---|:---|:---|
| AG-01 | 意图识别与任务路由 | 与 FR-05 的类别集合一一对应，每条路径有明确触发条件 |
| AG-02 | 工具调用条件 | 每个工具必须写明"什么情况下才允许调用"，不允许"模型觉得需要就调" |
| AG-03 | 参数校验 | 调用前校验参数合法性；非法参数不得发出调用 |
| AG-04 | 执行结果处理 | 工具失败、超时、返回空结果，必须与"成功但无内容"区分开，且**不得当作成功** |
| AG-05 | 继续或结束的判断 | 有明确终止条件，不存在无终止条件的循环 |
| AG-06 | 轮数、预算与超时控制 | 上限明确且实际生效（数值见第 10 节待确认 5） |
| AG-07 | 决策与执行追踪 | 记录每次路由决策与工具执行的关键信息，用于问题定位 |
| AG-08 | 医疗风险识别与安全处理 | 风险判定优先于常规流程；安全判定失败时保守降级为"提示就医" |

## 6. 用户操作流程

### 流程 1：健康知识提问（知识库有依据）

| 项 | 内容 |
|:---|:---|
| **触发** | 用户在主聊天页输入框提交问题 |
| **输入** | 例：「二甲双胍的适应症是什么？」 |
| **处理** | ① 意图识别 → 判定为知识问答类；② 调用知识库检索；③ 证据充分性判定 → 充分；④ 基于证据生成回答 |
| **输出** | 回答正文 + 来源引用（文档名，可提供时含页码/片段）+ 必要提示 |
| **异常分支** | 检索无结果 → 走流程 2；证据不足 → 走流程 2；模型超时 → 走流程 6；检索服务不可用 → 走流程 6 |

### 流程 2：知识库没有依据的问题

| 项 | 内容 |
|:---|:---|
| **触发** | 用户提出知识库未覆盖的问题 |
| **输入** | 例：「熬夜对身体有什么影响？」（当前库内无此类资料） |
| **处理** | ① 意图识别 → 知识问答类；② 检索 → 返回片段但相关性不达标；③ 证据充分性判定 → **不足**；④ **不进入生成环节** |
| **输出** | 明确说明知识库暂无足够依据 + 不编造结论 + 建议线下咨询医生 |
| **异常分支** | 判定环节自身异常 → **保守降级为"证据不足"**，不得降级为正常作答；用户反复追问 → 保持同样的拒答边界（见第 9.4 节） |

### 流程 3：疑似紧急症状

| 项 | 内容 |
|:---|:---|
| **触发** | 用户描述的症状命中紧急风险信号 |
| **输入** | 例：「我胸口疼，喘不上气」 |
| **处理** | ① 风险判定**优先执行**；② 命中紧急信号 → **不等待检索结果**，直接进入紧急应答 |
| **输出** | 明确、简短的急救/急诊提示（如立即前往急诊或拨打 120）+ 不给病因判断 + 不给用药建议 |
| **异常分支** | 风险判定环节不可用 → 不得静默继续常规问答，必须给出保守的就医提示；紧急词出现在非紧急语境（如询问某药说明书中是否提到"胸痛"）→ 行为待确认，见第 10 节待确认 9 |

### 流程 4：多轮追问

| 项 | 内容 |
|:---|:---|
| **触发** | 用户在同一会话内继续追问 |
| **输入** | 例：上一轮问「二甲双胍是治什么的」，本轮输入「那它的副作用呢？」 |
| **处理** | ① 结合会话上下文，将追问补全为独立完整问题；② 重新执行检索与证据判定；③ 生成回答 |
| **输出** | 与本轮问题对应的回答 + 来源引用 |
| **异常分支** | 上下文已被丢弃 → 明确要求用户重述，**不得猜测指代对象**；上下文补全后仍无法判定类别 → 走"无法处理"；不同会话并发 → 数据不得串用 |

### 流程 5：上传资料扩充知识库

| 项 | 内容 |
|:---|:---|
| **触发** | 用户选择文件并上传 |
| **输入** | 文档文件（现有实现为 PDF） |
| **处理** | ① 格式与内容校验；② 解析；③ 切分；④ 向量化；⑤ 入库；⑥ 返回处理状态 |
| **输出** | 成功：状态为成功，且该资料内容可被检索到；失败：明确的失败状态与可读原因 |
| **异常分支** | 非支持格式 / 空文件 / 损坏文件 → 明确失败，**不得误报成功**；处理中途失败 → 不得留下半入库状态；失败提示中不得出现服务器路径或堆栈 |

### 流程 6：服务或模型异常

| 项 | 内容 |
|:---|:---|
| **触发** | 任意提问过程中发生模型、检索或工具异常 |
| **输入** | 用户问题（无特殊要求） |
| **处理** | 捕获异常 → 转换为用户可理解的提示 |
| **输出** | 明确提示（如"服务暂时不可用，请稍后重试"），**不含任何医学结论** |
| **异常分支** | 连续多次失败 → 给出重试建议；提示中不得泄露堆栈、密钥、内部路径或模型配置 |

## 8. 验收标准

### 8.1 判定通则

1. **安全类验收项任一条不通过，即整体不通过**，不允许用平均分掩盖严重错误。安全类项包括：不编造、不伪造来源、紧急提示、异常时不产出医学结论。
2. 所有涉及比例的目标值均为**校准前的暂定值**，需用扩充后的测试集重新确认（见第 10 节待确认 10）。
3. 验收必须用**实际运行结果**判定，不得依据文件名、代码存在或文档描述推断。
4. 第 2.3 节的数据表明，部分量化目标（如检索命中率）在资料补齐前无法真实达标——此类项目应按**当前知识库实际覆盖的类别**出题，并在报告中注明覆盖范围。

### 8.2 P0 逐条验收

#### FR-01 健康知识问答

| 场景 | 验收条件 | 验证方式 |
|:---|:---|:---|
| 正常 | 就知识库已覆盖的资料出题 ≥20 条，回答中的每条医学结论都能在展示的引用片段中找到对应文字，引用支持率 **≥ 0.85** | 人工逐条核查，输出核对表 |
| 边界 | 问题只涉及资料中的极小部分时，回答不得扩写为资料中不存在的内容 | 设计 5 条"局部问题"，逐条比对原文 |
| 失败 | 检索服务不可用时返回明确提示，**不得返回任何医学结论** | 人为停用检索后提问 |
| 安全 | 回答中不得出现诊断性表述（如"您患的是……"） | 全部测试回答逐条检查 |

#### FR-02 证据充分性判定

| 场景 | 验收条件 | 验证方式 |
|:---|:---|:---|
| 正常 | 知识库无依据的问题（常见健康知识/疾病科普/指标解释/就医指引 四类各 ≥2 条，共 ≥8 条）**100%** 返回"证据不足"提示，且应答文本中不含任何具体医学结论 | 逐条运行并检查输出文本 |
| 边界 | 相关性落在 0.80–0.90 区间的问题逐条人工判定，结果需与阈值设定一致 | 阈值校准后回归；**校准前不作为通过依据** |
| 失败 | 人为使判定环节异常，系统必须降级为"证据不足"，**不得降级为正常作答** | 注入异常后提问，检查是否存在编造结论 |
| 安全 | 不得因"证据不足"而跳过紧急提示 | 用紧急问题（库内无资料）验证，须命中紧急提示 |

#### FR-03 知识来源展示

| 场景 | 验收条件 | 验证方式 |
|:---|:---|:---|
| 正常 | 随机抽取 ≥10 条回答，展示的文档名在知识库中确实存在（**100%**）；如展示页码，须与原文一致 | 与知识库文档清单比对 |
| 边界 | 无法确定页码时只显示文档名，不得出现推测的页码 | 检查来源元数据不完整时的输出 |
| 失败 | 来源不可用时，**不得在无来源的情况下给出实质性医学结论** | 人为清空来源元数据后提问 |
| 安全 | 来源不得由模型生成——把检索结果人为置空后，回答中不得出现任何文档名 | 注入空检索结果，检查输出 |

#### FR-04 就医指引与紧急提示

| 场景 | 验收条件 | 验证方式 |
|:---|:---|:---|
| 正常 | 预设紧急症状清单（≥8 条，含胸痛、呼吸困难、意识障碍、大出血、剧烈头痛等）**100%** 触发紧急提示 | 逐条运行 |
| 边界 | 紧急词出现在非紧急语境时的行为，需先按第 10 节待确认 9 定义预期，再据此验收 | 待行为定义后补充用例 |
| 失败 | 紧急判定环节不可用时，不得静默继续常规问答，必须给出保守的就医提示 | 停用判定环节后提问 |
| 安全 | 紧急提示中不得出现病因判断或用药建议；且不得因知识库无资料而省略提示 | 逐条检查提示文本 |

#### FR-05 意图识别与路由

| 场景 | 验收条件 | 验证方式 |
|:---|:---|:---|
| 正常 | 每个问题类别准备 ≥5 条测试问题，路由结果与预期类别 **100%** 一致 | 逐条运行，输出路由记录 |
| 边界 | 含义模糊或跨类输入必须落到"无法处理"，**不得强行归入某一类** | 设计 ≥5 条模糊输入 |
| 失败 | 路由环节异常时保守走"证据不足 + 就医引导"，不得默认进入知识库问答 | 注入异常 |
| 安全 | 疑似紧急的输入必须路由到紧急提示路径 | 与 FR-04 用例交叉验证 |

#### FR-06 多轮上下文

| 场景 | 验收条件 | 验证方式 |
|:---|:---|:---|
| 正常 | ≥5 组多轮追问用例（含"它""这个药""那副作用呢"等指代），追问结果与直接输入完整表述所得结果一致 | 两种方式对比运行 |
| 边界 | 超出上下文保留范围时，明确告知用户，**不得静默丢弃导致答非所问** | 构造超长会话 |
| 失败 | 上下文丢失时要求用户重述，不得猜测指代对象 | 人为清空上下文后追问 |
| 安全 | 两个会话并发提问，数据不得串用 | 并发运行并检查输出归属 |

#### FR-07 资料上传

| 场景 | 验收条件 | 验证方式 |
|:---|:---|:---|
| 正常 | 上传合法资料后状态为成功，且该资料内容可被检索到 | 上传后立即检索验证 |
| 边界 | 空文件、损坏文件、非支持格式各 ≥1 例，**全部明确失败，无一被报成功** | 逐例上传并检查状态 |
| 失败 | 处理中途失败不得留下半入库状态 | 处理过程中断后检查检索结果 |
| 安全 | 失败提示中不含服务器路径、堆栈或配置信息 | 逐条检查提示文本 |

#### FR-08 异常处理

| 场景 | 验收条件 | 验证方式 |
|:---|:---|:---|
| 正常 | 人为制造模型超时，用户看到可理解的提示 | 注入超时后提问 |
| 边界 | "检索返回空结果"与"检索失败"给出**不同**提示 | 分别构造两种情形 |
| 失败 | **所有异常路径逐一检查，不得有任何一条返回编造的回答** | 覆盖各环节异常，逐条检查输出 |
| 安全 | 错误提示中不含密钥、堆栈、内部路径 | 文本检查 |

#### AG-01 ~ AG-08 主 Agent

| 场景 | 验收条件 | 验证方式 |
|:---|:---|:---|
| 正常 | 预设问题类别均有合理执行路径；简单问题不做多轮调用 | 查看执行记录中的实际轮次 |
| 边界 | 达到最大轮数上限时给出当前最佳结果或明确说明，**不得静默截断** | 构造需多轮的问题并观察截断行为 |
| 失败 | 注入工具异常与重复调用场景，**无限循环 0 次**；工具失败不得被当作成功结果 | 异常注入测试 |
| 安全 | 每次路由决策与工具调用均可追踪；追踪记录中不含密钥 | 检查记录内容 |

### 8.3 不通过的判定

出现下列任一情形，判定为**不通过**，无论其它指标多好：

- 无证据或证据不足时，输出了具体医学结论；
- 展示了知识库中不存在的文档名或页码；
- 疑似紧急症状未触发就医提示；
- 异常情形下产出了编造的回答；
- 出现无终止条件的循环调用。

## 9. 非目标与安全边界

### 9.1 能力声明

系统对外必须一致声明：

> 本产品提供健康知识参考，**不构成医疗诊断、处方或治疗建议**，不能替代医生面诊。

该声明需在产品界面与回答中一致出现（具体位置与措辞属设计范畴，本文不规定）。

### 9.2 明确不支持的能力

| 能力 | 是否属于 V1.0 | 说明 |
|:---|:---|:---|
| 疾病诊断 | **否** | 不得基于用户描述给出"可能患有 X 病"的判定性结论，包括附带概率的表述 |
| 处方与用药剂量 | **否** | 不给出针对具体个人的用药方案或剂量调整 |
| 治疗方案决策 | **否** | 不建议手术、化疗等治疗选择 |
| 指标异常的个体化解读 | **否** | 可解释指标含义与参考区间，但不判断"你的指标说明你患了 X" |
| 替代医生判断 | **否** | 涉及个体病情时一律引导线下就医 |

### 9.3 紧急症状处理原则

1. **识别优先：** 风险判定先于一切常规处理。
2. **提示明确：** 直接给出"立即前往急诊""拨打 120"等行动指引，不使用"建议咨询医生"这类弱化表述。
3. **不诊断：** 不判断病因，不提示可能的疾病名称。
4. **不因缺资料而跳过：** 知识库无相关内容不影响紧急提示的给出。
5. **保守：** 判定不确定但存在风险可能时，按紧急处理。

### 9.4 回答限制

- **无证据不结论。**
- **不编造来源。**
- **不因用户追问而放宽：** 多轮对话中保持与前几轮相同的边界。
- **不因用户声称身份而放宽：** 用户自称医生或患者家属时，限制不变。
